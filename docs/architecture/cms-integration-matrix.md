# CMS-to-public integration matrix

Where every public route and section gets its content, how it is edited, published and invalidated, and how it is verified. Decisions: [ADR 0007](../decisions/0007-cms-editorial-workflow.md), [0011](../decisions/0011-content-revisions.md), [0012](../decisions/0012-cms-page-registry-seo-and-settings.md), [0013](../decisions/0013-designed-sections-in-the-cms.md).

**Legend**

- **Workflow D→R→P→A**: Draft → In review → Published → Archived, with pending revisions for published items (ADR 0011). Settings are live on save (administrators only, audited).
- **Tags**: `"use cache"` tags expired with `updateTag` when content goes live, changes while live, or leaves the site (`src/lib/cache-tags.ts`). `content:` prefix omitted below.
- **Sections**: designed sections declared in code and edited in the CMS (ADR 0013): `pages.content` validated by `landing-content.ts` or `home-content.ts`, `programmes.content` by `designed-content.ts`. Editors change words, list items, images, link destinations and placeholder markers; the composition and design stay in code.
- **Code-owned**: kept in code by rule (ADR 0013): the protected brand, integrity statements, notices about website features that do not exist yet, the placeholder register, reference specimens and interface labels. Listed at the end.
- **Verified by**: `U` = `tests/unit/pages.test.tsx` (every route renders from the seeded database with one h1, metadata and indexing rules, and shows every seeded section word); `S` = `tests/unit/sections.test.ts` (declarations, seed validity, form round trip, validation, backfill); `I` = `tests/integration/*.test.ts`; `E` = `tests/e2e/admin.spec.ts`. Results are in the [M04 CMS verification report](../audits/M04-cms-verification.md).

## Kept in code by rule (ADR 0013)

M04 content remediation: public project/resource list components omit sample records and show controlled explanatory notices when no eligible record is available; sample detail routes and their indexing safeguards remain unchanged. Review field patches live in `docs/content/cms-review-proposals.json`, with readable copy in [client review](../content/CLIENT-CONTENT-REVIEW.md). The explicit dev-only `scripts/prepare-content-review.ts` creates DRAFT `content_revisions` from current editor fields, skips existing revisions and never writes a live content row. It is not run by the normal seed; submit/approve and publication validation remain the existing CMS workflow. It creates no named people, new partners, projects, publications or contact settings.

## Approved content implementation

The owner reports client approval except contact and location information. `docs/content/approved-content.json` supplies approved seed defaults; existing records are updated only by the explicit dev-only `scripts/apply-approved-content.ts`, using the same editor parsers, save adapters and publishing checks as the CMS. The script records review/publication audit events with a system actor and the external authority; it refuses unrelated pending revisions. Public cache refresh requires rebuilding/restarting after this CLI operation. Normal staff publication still uses the existing cache invalidation and server authorisation.

Three starter project records have operational status PLANNED, no locations/dates, no assigned partners and no outcomes. Three educational GUIDE articles are new website copy, not historical research papers. The normal seed remains create-only for existing values. `PendingContent` renders nothing for approved ledger keys; only contact and location keys retain visible notices. Missing legal/history facts are omitted from About, rather than shown as empty facts. No schema, authentication integration or public form was added.
